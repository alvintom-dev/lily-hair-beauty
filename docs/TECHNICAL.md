# Technical notes

Engineering detail for the Lily Hair and Beauty House site. Day-to-day editing is covered
in the [README](../README.md).

---

## Shape of the thing

One HTML file. No framework, no bundler, no build step. ES5-compatible JavaScript in a
single IIFE, CSS inline in `<head>`, content held in plain arrays near the top of the
script. `index.html` is ~1700 lines and ~100 KB raw (28 KB gzipped, 23 KB brotli).

```
index.html      markup + CSS + JS + content
404.html        standalone, no shared assets
_headers        Cloudflare Pages / Netlify cache + security headers
deploy.sh       stage dist/ and push to Cloudflare Pages
add-photo.sh    encode one photo into 6 variants
images/hair_styles/<name>-{400,800,1200}.{avif,webp}
assets/         logo (webp 220/440), favicon, apple-touch-icon
```

## Content lives in arrays

All editable business content sits in one block at the top of the script:

| Array | Drives |
| --- | --- |
| `WA` | Every WhatsApp deep link |
| `HOURS`, `TZ` | The live open/closed badge |
| `LOOKS` (6) | Hero strip, lookbook, gallery, style-preview picker |
| `SERVICE_INFO` (9) | Services grid, booking dropdown, quiz scoring; `SERVICES` is derived from it |
| `BA` (3) | Before/after blocks |
| `QUIZ` (4) | Style Finder; scoring in `recommend()` |
| `TIMES` | Booking slot chips |

`LOOKS` is deliberately one array feeding four sections — the earlier version had a
5-entry `LOOKS` and a separate 6-entry `HERO_CARDS` that had already drifted out of sync.

## Rendering

`pic(base, alt, sizes, opts)` emits `<picture>` with an AVIF `<source>` and a WebP `<img>`
fallback across 400/800/1200. It assumes **all six files exist** for a base name;
`deploy.sh` refuses to deploy if any are missing.

Sections built from data at runtime: hero strip, lookbook + thumbnails, before/after,
gallery, services grid, booking slots, style-preview choices.

## Hero

A 520vh sticky track (360vh under 900px) with a horizontal strip scrubbed by scroll.

- **≥ 900px**: GSAP + ScrollTrigger are injected dynamically for the scrub and per-card
  parallax.
- **< 900px**: a built-in rAF-throttled fallback (`paint()`) moves the same strip. GSAP is
  never requested on a phone — 113 KB saved.
- **Card reveals** are CSS + `IntersectionObserver`, not ScrollTrigger, so they fire on
  both paths. ScrollTrigger's `containerAnimation` triggers did not fire for cards already
  on screen at load, which left their captions stuck at `opacity: 0`.
- `--heroLen` is set **in CSS, not JS**. An inline style set from JS silently overrode the
  media query and never re-evaluated on resize.

## Before/after slider

- Pointer capture is bound to the **handle only**. The frame is `touch-action: pan-y`, so a
  swipe over the photo scrolls the page instead of dragging the divider.
- The handle is a real `role="slider"`: arrows ±2%, Shift ±10%, Home/End to the ends.
- A plain click anywhere on the frame also jumps the divider — a click can never be a scroll.
- Position is one CSS custom property `--p` on the frame; the divider, the handle and the
  after-image's `clip-path` all read it.
- The divider is drawn twice — dark dashes with white dashes over them — so it stays visible
  on both light and dark hair.

## Overlays

The WhatsApp drawer, map sheet and owner panel share one manager (`openOvl` / `closeOvl`)
that locks background scroll, moves focus to the close button, restores focus on close,
handles Escape, and keeps a stack so two overlays close in the right order.

`openOvl` adds its `.open` class via double-rAF **and** a 60ms timeout fallback — rAF is
suspended in a backgrounded tab, which would otherwise leave a panel permanently invisible.

## Opening hours

`studioClock()` reads the current time via `Intl.DateTimeFormat` with `timeZone:'Asia/Kuching'`.
Using the visitor's device clock would tell someone browsing from another timezone the wrong
thing. Falls back to hiding the badge entirely if `Intl` timezone support is missing.
Re-renders every 60s. `nextOpening()` walks forward up to 8 days, so Saturday evening
correctly reports "opens Monday".

Every hours string on the page — the contact card's two rows, the footer, the map panel and
the mobile menu — is generated by `paintHoursText()` from `HOURS`. Editing the constant is
the whole change; the four copies cannot drift apart. `daysLabel()` collapses a contiguous
run to `Mon – Sat` and falls back to a comma list for scattered closures.

## Gotchas worth remembering

- **`img { height: auto }` is load-bearing.** The `width`/`height` HTML attributes become a
  presentational `height` hint, and an explicit height silently overrides `aspect-ratio`.
  Without it, `aspect-ratio: 4/5` did nothing and images kept their full intrinsic height.
- **Preload and `<picture>` must agree.** The hero preload uses `imagesrcset`/`imagesizes`
  matching the first card's `sizes` exactly. If they diverge the browser downloads two
  copies of the same photo.
- **`404.html` is required.** Without it Pages serves `index.html` with a **200** for every
  unknown path — thousands of soft-404s for search engines.
- **`minmax(min(100%, Npx), 1fr)`**, not `minmax(Npx, 1fr)` — the latter overflows below
  N px and `overflow-x: hidden` on `body` hides the evidence.
- Form fields are 16px because anything smaller makes iOS Safari zoom on focus.
- A `<button>` cannot contain `<h3>`/`<div>`. Hero cards are `<article>` with an absolutely
  positioned `.hcHit` button covering them.

## Breakpoints

| Width | Behaviour |
| --- | --- |
| ≤ 340px | Hero card captions hidden (they collided with the progress row) |
| ≤ 600px | Gallery 2-up, services 1 column |
| ≤ 680px | Enquiry drawer becomes a bottom sheet |
| ≤ 900px | Burger menu, no GSAP, hero track 360vh |
| ≥ 820px | Before/after two-column, alternating sides |
| ≥ 860px | Lookbook two-column |
| ≥ 1000px | Gallery 6-up, services 3 columns, contact 4 columns |

## Performance

Desktop first load ≈ 150 KB, of which GSAP is 113 KB. Mobile ≈ 35 KB plus one hero image.

- Stylesheet is inline — first paint needs no extra round trip.
- Fonts load non-render-blocking (`media="print"` swapped on load) with a `<noscript>`
  fallback; only the four weights actually used are requested.
- All imagery is local AVIF/WebP. Zero third-party image requests.
- Everything below the fold is `loading="lazy"`.
- The Google Maps iframe loads only when the map sheet is first opened.
- `prefers-reduced-motion` collapses the hero to one screen and disables transitions.
- The `#bgFx` backdrop is a ~1 KB SVG line-art tile (`assets/bg-pattern.svg` — strands,
  a curl, scissors, a comb; motifs kept inside the tile so the repeat is seamless).
  Its lightness is baked into the strokes. The drift runs inside the existing scroll
  rAF via `paintNav()`; static below 900px and under reduced-motion. The page
  background lives on `<html>` because a negative-`z-index` child only paints above
  the canvas when `body` is transparent. `deploy.sh` copies the SVG by name — new
  asset files must be added to its whitelist or they never publish.

## Hosting

Cloudflare Pages, project `lily-hair-beauty`, account `alvintom.dev@gmail.com` (BOSZ).
Custom domain `lily-beauty.baratech.my` — a CNAME to `lily-hair-beauty.pages.dev` in the
`baratech.my` zone, proxied.

`deploy.sh` stages a clean `dist/` (excluding `assets/hero/`, `images/h_s_*` and the
unreferenced source PNG), verifies every look has all six image variants, then does a
direct upload. It reuses the `wrangler` pinned in `baratech/baratech-landing/node_modules`
when that repo is checked out alongside this one.

Note the wrangler OAuth token carries `pages (write)` but **not** DNS write, so a new
custom domain needs its CNAME created by hand in the dashboard.

The production domain appears in `index.html` in four places — the canonical link,
`og:url`, `og:image` and the JSON-LD `image`. `og:image` must stay absolute; social
scrapers don't resolve relative URLs. Nothing else is domain- or host-specific: `dist/`
serves unchanged from any static host.

### Elsewhere

Any static host works with no build command, publishing `dist/` (or the repo root).
`_headers` is read by Cloudflare Pages and Netlify. Vercel equivalent:

```json
{
  "headers": [
    { "source": "/(images|assets)/(.*)",
      "headers": [{ "key": "Cache-Control", "value": "public, max-age=31536000, immutable" }] },
    { "source": "/index.html",
      "headers": [{ "key": "Cache-Control", "value": "public, max-age=0, must-revalidate" }] }
  ]
}
```

## If Lily needs to edit it herself (future option)

Not built. Written down so the decision is ready when it's needed.

**Today's split works if the people editing are comfortable with a text editor and one
Terminal command.** Both content and code live in `index.html`, which is exactly what keeps
the site at 35 KB on a phone with no build step. The cost is that a non-technical person
cannot safely edit it — one deleted comma blanks the page.

### What would change, and what would not

Adding a CMS **does not touch the photos**. The six studio looks in `images/hair_styles/`,
the `LOOKS` entries pointing at them, and every service description stay exactly as they
are. A CMS only changes *where the text lives* — moving the arrays out of `index.html` into
a file the admin screen writes to. The site renders the same, from the same images.

### The option worth taking

**Sveltia CMS** (or Decap, its older sibling) on Cloudflare Pages:

- One extra file, `admin/index.html`, and a config listing the fields Lily may edit.
- She visits `lily-beauty.baratech.my/admin`, logs in with GitHub, and edits prices, hours
  and text in form fields. Works on her phone.
- Saving commits to the repo, which triggers a deploy. No Terminal, no code.
- Image uploads go through the same screen — though they'd bypass `add-photo.sh`, so
  they'd be a single unoptimised file rather than six sizes. Either accept slightly
  heavier images for CMS uploads, or keep photos as a developer job.

**What it costs:** content moves from `index.html` arrays into `content.json` (or per-item
Markdown), and the page fetches it. That means a build step or a fetch-on-load, and the
current single-file simplicity goes away. Half a day of work, plus GitHub auth setup.

**What it does not solve:** bookings still land in WhatsApp, and the owner view is still
`localStorage`. A CMS is for editing the site, not for receiving enquiries.

### Cheaper half-measure

Move only `SERVICE_INFO`, `HOURS` and `WA` into a small `content.json` that the page
fetches. Lily could edit that in GitHub's web editor — still JSON, still breakable by a
stray comma, but a 20-line file instead of a 1700-line one, and GitHub flags invalid JSON
before saving. No build step, no auth setup.

### Recommendation

Stay as-is while the two of you are the only editors. The moment Lily wants to change a
price without messaging anyone, do the Sveltia option properly rather than the half-measure
— a JSON file she can still break is not much of an improvement over what exists now.

## Future: AI-enhanced quiz (shelved)

Decided and designed, deliberately not built yet. The Style Finder would keep its
rule-based result — rendered instantly, as today — while a background call upgrades only
the prose when an AI endpoint answers. Every failure mode (endpoint down, no credits,
timeout, bad JSON, flag off, non-Cloudflare host) is invisible: the local result stays.

Agreed design:

- **Flag:** `AI_QUIZ = true` in `index.html` (same pattern as `SHOW_AI_STUDIO`). Ships
  on; set `false` to kill the feature entirely.
- **Endpoint:** a Cloudflare Pages Function, `POST /api/recommend`, accepting only the
  four fixed quiz answers (whitelisted strings, no free text), returning `{why, tip}`.
- **Provider:** Kimi (Moonshot) OpenAI-compatible chat API. Key in `wrangler secret`,
  model name in an env var. Low temperature, strict JSON, length-capped client-side.
- **Scope:** prose only. `recommend()` always picks the service, so the model can never
  invent one Lily doesn't offer.
- **Client:** fetch with a ~3s timeout after the local result renders; swap the "why"
  paragraph on success, silently discard otherwise. No badge, no loading state.
- **Prerequisites (why it's shelved):** a Cloudflare rate-limit rule on
  `/api/recommend/*`, Bot Fight Mode, and a spending cap on the Kimi key. The endpoint
  spends real money, so abuse protection comes first.
- **Portability:** the enhancement is Cloudflare-only. On any other host the endpoint
  404s and the quiz behaves exactly as it does today — the static site loses nothing.

## Known limitations

- **There is no inbox.** Enquiries and booking requests go to Lily's WhatsApp and nowhere
  else. (The pre-launch "Owner view" demo — `localStorage`-only leads — was removed.) A
  real inbox would need a backend.
- **The AI Studio is off** (`SHOW_AI_STUDIO = false`). Its three tools run on local keyword
  matching, with no model behind them.
- **The gallery repeats the hero photos.** Six source images serve four sections. Fine for
  placeholders, obvious once real client work exists.
- Prices live in `SERVICE_INFO[].price`. `dur` is optional — the duration pill only renders
  when a service defines one, and none currently do (the client gave prices, not durations).
- Renaming a service means updating `recommend()` in the quiz, `LOOKS[].service` and
  `BA[].service`, which all match on the name string. `SERVICES` derives from
  `SERVICE_INFO`, so the booking dropdown follows automatically.
- The JSON-LD has no `geo`. Sibu Jaya Shopping Centre 2 is absent from OpenStreetMap and
  the coordinate could not be verified; an approximate one for a real business is worse
  than none. Restore it from a Google Business Profile.
- Map and Waze links pass the address as a search query rather than coordinates, for the
  same reason.
